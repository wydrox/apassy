**Decision: NO-GO for an unattended Mac-first rollout.** A schema-19 iPhone cannot consume a schema-20 synced vault. Obtain and verify a schema-20 TestFlight build before publishing the Mac update, then coordinate installation on every reader before reopening the shared vault. Uploading TestFlight first is preparation: opening that new iPhone app against the shared vault first can also advance its schema and strand old Macs. Neither direction makes an uncoordinated rollout safe.

## 2. Vault migration and fleet compatibility

**Local file: migration happens during successful unlock, immediately.** Merely discovering/opening a locked `Vault` is not migration. `Vault::unlock` calls `open_working_conn` (`src/vault/mod.rs:263–273`); after validating the file, that function migrates any earlier schema before returning (`src/vault/mod.rs:1334–1366`). The migration is one immediate transaction (`src/vault/mod.rs:1201–1206`, `1271–1276`) and sets both `vault_meta.schema_version` and `PRAGMA user_version` to 20 (`src/vault/schema20.rs:83–91`). It does not wait for the owner to edit a credential.

**iCloud file: the app keeps a separate local working vault; the shared file is a closed encrypted snapshot.** The Mac never opens SQLite directly in the sync folder (`src/sync/mod.rs:4–17`). A successful sync that reads an older snapshot will write schema 20 even if its credential content is unchanged (`src/sync/mod.rs:649–666`; `src/vault/merge.rs:1179–1183`). Existing cached folder state can defer that rewrite until a remote snapshot is read or content needs pushing: `local_changed` compares content, and `outdated` is detected only on the fetch/merge path (`src/sync/mod.rs:583–588`, `643–664`). **Do not rely on “I have not edited anything” as a migration grace period.** iPhone sync explicitly writes a newer-schema snapshot with no edit (`ios/ApassyCore/src/core/icloud.rs:515–538`; regression source `ios/ApassyCore/tests/icloud_flow.rs:936–976`).

| Reader/writer during the gap | Consequence |
| --- | --- |
| iPhone actually running a released schema-19 core (including a normal 0.5.7 build from `a1524ca8`) | Cannot read/import/merge schema 20. Its existing schema-19 local vault can remain usable, but sync is blocked and new Mac changes are unavailable; a direct schema-20 open fails. Thus the phone can be locked out of the **shared current vault**, even when an old local copy still opens. Source 0.5.7 has `SCHEMA_VERSION = 19` (`a1524ca8:src/vault/types.rs:22`); iOS uses that same core schema (`ios/ApassyCore/Cargo.toml:15`; `ios/ApassyCore/src/core/mod.rs:55–56`). | Another Mac still on 0.5.7 | Rejects a newer snapshot/open as `UnsupportedSchema`; it cannot safely participate in schema-20 sync until updated. ## 6. Rollback and recovery

- **Before the first schema-20 unlock/sync:** keep clients locked, stop the rollout, and use the preserved signed 0.5.7 app and verified schema-19 backup if installation rollback is needed. Retain exact artifacts/SHAs; R2 removes the previous versioned DMG after successful publication (`.github/workflows/release.yml:410–430`).
- **After schema 20 is written:** 0.5.7 cannot open it. Prefer a fix-forward coordinated **0.5.9** with green checks and a new version across all six components. Replacing only the Mac app with 0.5.7 is not a vault rollback. Do not run the test-only schema downgrade helper, delete bouncer tables, lower `user_version`, or assume uninstalling reverses migrations.
- A destructive data rollback requires separate owner approval: stop every writer/transport, preserve current encrypted files for recovery, restore the pre-upgrade encrypted backup into a deliberate recovery setup, and reconcile newer changes before rejoining other devices. An old snapshot reintroduced to active sync can be merged or overwritten; restoring the shared file alone is unsafe. Restoration can lose post-backup changes. Older writers' already-pruned tombstones are not reconstructed by upgrading.
- Do not lower public `latest.json` or republish the same 0.5.8 as a recovery release. Installed updaters compare versions, and the production gate requires strictly greater SemVer (`docs/operations/release.md:10–20`; `scripts/ci-release-newer.py:64–74`). Preserve exact failed-release evidence while preparing a new patch.
- For an approved version-only relay rollout, preserve the old CI image/compose state and backup. Server schema stays 6/directory 1003; rolling back only the image to the same-schema prior release should not require restoring DBs. Verify observed schemas first. Any data restore is a separately approved recovery with data-loss implications. Do not use historical schema-3/4 rollback commands from the app runbook for this release.
- Reverting the CWS package is another store upload requiring a higher version and owner action; it is not an instantaneous downgrade. Holding CWS automatic publication is the safer control during this migration.
