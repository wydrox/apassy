## Recommendation

Add one **How often to ask** choice under **Settings > Security > Browser approvals**, with **Every time** as the unchanged default and **1 minute / 5 minutes / 15 minutes** as explicit alternatives. It controls repeated identity verification for routine browser password and code actions on this Mac, in the current vault. A five-minute choice is a useful starting recommendation for an owner who wants fewer Touch ID prompts; do not silently migrate anyone to it. Keep an explicit action confirmation in Apassy during a window. This replaces repeated biometrics with one click, rather than letting a page, socket client, or agent spend recent authentication silently. This is a reduction in identity prompts, not removal of consent. **Hick's Law**, **Default Bias**, and **Feedback Loop** support one bounded choice, unchanged defaults, and visible state.

Keep passkey creation and assertion freshly verified in v1. They currently claim user presence and user verification in signed authenticator data; changing their verification policy requires a separate authenticator design. Keep agent approvals and every action that grants durable authority freshly checked too. This deliberately leaves some of the owner's passkey complaint unresolved; do not market the setting as applying to all approvals.

## Part 1 — Map

### Counting and frequency assumptions

There are **49 `OwnerRequest` variants** in `src/desktop/owner_check.rs:228` and **40 `OwnerAction` variants** in `src/broker/approvals/owner_auth.rs:88`. Several UI requests share a proof action, and the action enum includes a legacy first-use grant and a non-required removal proof. These are not 89 separate prompts. The tables account for every variant, plus unlock, settings checks outside that gate, and mobile gates. A source-only enumeration was used for the counts.

Daily estimates are planning ranges for an active owner using the browser and agents during a working day, **not measured usage**. An illustrative day has 2–6 vault unlocks/switches, 8–20 browser password fills, 1–5 code fills, 1–6 passkey assertions, 0–3 save/create/update actions, and 2–15 manually answered agent questions. Setup and policy edits normally occur zero times on an ordinary day. These ranges overlap across devices and alternatives and must not be added together. Actual counts remain UNKNOWN until the owner measures them; do not inspect their vault for this audit.

**Methods:** **T/P** = macOS LocalAuthentication Touch ID, with Apassy master-passphrase fallback. It is not a macOS account-password fallback. **F/P** = fresh iPhone Face ID/Touch ID, with vault-passphrase fallback. **SE** = per-answer Secure Enclave approval-key signature requiring fresh biometry, without passcode or vault-passphrase fallback. **R** = signature verification on the receiving Mac, with no additional local biometric prompt.

**Common desktop gate:** `DesktopApp::ask_owner` → `start_owner_check` → `OwnerGate::authorize_cancellable` (`src/desktop/owner_check.rs:1505`, `:1571`; `src/broker/approvals/owner_auth.rs:980`). A ready request starts Touch ID automatically when available. Multiple passkey accounts must be chosen first (`owner_check.rs:575`, `:581`, `:1551`; `browser.rs:731`). `native/ApassyHelper/Auth.swift:43` makes a new `LAContext`; `:78` evaluates `.deviceOwnerAuthenticationWithBiometrics`. No macOS `touchIDAuthenticationAllowableReuseDuration` assignment or application authentication grace window was found. Authentication readiness/capability probes do not authenticate anyone.

**Common proof rule:** `OwnerProof` is non-Clone, action-bound, vault-epoch-bound, and valid for 60 seconds (`owner_auth.rs:78`, `:860`, `:927`). That minute lets the authenticated action finish; it does **not** authorize another action. Passphrase verification reopens/checks the file (`:1043`). Queue/session checks afterwards are proof validation, not additional owner prompts (`src/broker/approvals.rs:703`; `src/desktop/owner_store.rs:1714`).

### Duplicate and repeated-prompt findings

1. **One website login can produce two biometric prompts:** FillLogin followed by FillCode (M06/M10). They authorize different outputs, but the second identity check during the same human login is the strongest routine reuse candidate. Save/create does not internally ask again to fill.
2. **Unlock then immediately fill/reveal/approve** causes a second identity check today (M01 plus subsequent action). It is intentional separation, not a hidden two-call bug. Recommendation: preserve this separation for v1 and seed only from a completed eligible browser check; otherwise simple unlock unexpectedly opens new authority.
3. **Show then Copy**, or code Show then Copy, authenticates twice (M03/M04/M05; I02). Direct Copy already avoids Show. Keep the separate checks: copying creates another exposure route. Improve discoverability of direct Copy rather than sharing a reveal proof.
4. **Development correction then Allow Once** needs two checks because the correction leaves the run waiting (`decisions.rs:2211`, `owner_check.rs:1748`). The existing PR #28 “allow once and evaluate” path combines its own run/classification/evaluation scope in one authenticated action; do not replace this with a generic grace bypass. A dedicated “Mark Development and allow once” composite proof would be a separate product/security change, not part of these units.
5. **Passkey create then immediate get** is two WebAuthn ceremonies, normally two fresh checks. Choosing an account plus Touch ID is one identity check plus selection. Native AutoFill and extension are separate routes, not intentionally chained providers.
6. **Cancel/failure then passphrase** can feel like two prompts. Mac `owner_check.rs:2298` keeps the dialog for fallback; iOS `OwnerGate.swift:45` falls back to a passphrase sheet. These are failed/cancelled attempt plus fallback, not two successful required verifications. Preserve failure invalidation; do not seed a window from failure.
7. **No duplicate biometric from receiver verification.** Relay/companion receiver checks signatures, not the owner again. iPhone Requests unlock plus approval-key Face ID can be two checks, intentionally: reading a card and signing authority are separate. Batch vault reopen already reduces unlock duplication.
8. **No after-check WebAuthn fallback duplication is intended.** `extension/passkey-page.js:12` and `passkey-bridge.js:76` prohibit fallback after a request reached the owner-check phase. Verify the phase boundary with tests; an unsupported/no-match/locked pre-check response may use the browser provider. Never retry a created credential after consent merely to reduce friction.

The audit found no clear static call path that requires two successful Touch ID evaluations for a single ordinary FillLogin, CreateLogin, or iOS AutoFill request. Native/device behavior has not been measured.

## Part 2 — Design

### 2.1 Scope and options

Use **one setting**, explicitly scoped to routine browser approvals on **this Mac and this vault file**. Separate fill/save/passkey/agent timers would multiply choices and make it hard to know which identity check still applies (**Hick's Law**, **Recognition Over Recall**). Do not add an agent timer under the same label.

| Choice | v1 | Rationale |
| --- | --- | --- |
| Every time | Default | Preserves current guarantees until owner opts in; no grace record. |
| 1 minute | Offer | Covers a password + code sequence or a short save/update sequence with a small exposure interval. |
| 5 minutes | Offer; recommend when opting in | Covers a short cluster of browser activity without an hour of unattended identity reuse. |
| 15 minutes | Offer; visibly longest choice | Supports a longer task with a fixed upper bound. Still ends earlier on every invalidating event. |
| 1 hour | Defer | Greater unattended exposure with modest benefit over 15 minutes and re-verification. No measured owner usage justifies it yet. |
| Until the Mac locks or sleeps | Defer | Potentially unbounded on a desktop. This revision lacks the necessary lifecycle observer. Implement lock/sleep invalidation for every offered duration first. |
| Never | Do not offer | Would remove an identity boundary instead of controlling its frequency. |

These durations are product choices, not a claim that Apple LocalAuthentication supports the same reuse periods. The application owns the window. Apple documents its own separate Touch ID reuse limit, so do not implement 15 minutes by setting `touchIDAuthenticationAllowableReuseDuration`. See [Apple LAContext reuse documentation](https://developer.apple.com/documentation/LocalAuthentication/LAContext/touchIDAuthenticationAllowableReuseDuration).

**Eligible in v1:** `FillLogin`, `SaveLogin`, `CreateLogin`, `UpdateLogin`, `FillCode`, only when delivered through a live browser request with verified signed host/browser identity and confirmed for this exact action in the local Apassy UI. Source builds / missing guard / legacy direct socket clients always require fresh authentication; a caller-supplied “human” flag or window token is never sufficient. Both timed and Every time modes keep all site/account/revision/form/document checks and app-side generation.

**Always fresh:** vault unlock; Show/Copy/large type and OTP Show/Copy; passkey get/create/removal on every platform; native macOS AutoFill; all agent run/grant/project/pattern/evaluation/production approvals; environment/rule/access relaxations; token issuance/lifetime; CLI login and sensitive CLI commands; model/calibration authority changes; new trusted device/pairing; enabling a remote approval channel; export or resume export; the new setting itself. Fresh actions do not seed or extend this browser window. Reasons: clear exposure to arbitrary software or humans, account authentication, irreversible key change, or durable/process/remote authority. Stronger policy that currently requires no check stays one click and never needs a new approval merely because a window exists.

**Security settings and export accuracy:** this does not retroactively claim all existing settings/export paths are gated. Current passphrase rekey uses the current passphrase; Touch ID disable, iPhone lock/clipboard pickers, encrypted Mac backup, and decision-log export have the exemptions in M33/M39/I07. Preserve them. Any newly introduced plaintext secret/key export must receive an explicit fresh export proof; do not reuse browser verification. Hardening unrelated existing controls would be separately scoped work.

**Passkeys:** keep fresh `SignPasskey/CreatePasskey` regardless of the choice. `src/vault/passkey.rs:94` and `:994`/`:1031` currently set UP/UV; neither cached vault-unlocked state nor a page JS event can justify asserting a fresh verified ceremony. The W3C defines an operation's authorization gesture and requires verification when required; this is the basis for the conservative v1 choice, not a claim that every possible session-aware authenticator is forbidden. A future proposal must explicitly address `userVerification` required/preferred/discouraged, per-request presence/consent, truthful flags, browser validation, OS provider contracts and account selection. Do not just change the flag or reuse Touch ID and call the passkey feature done. [WebAuthn Level 3, authenticator operations](https://www.w3.org/TR/webauthn-3/#sctn-authenticator-operations).

### 2.2 Protected storage

Store the **policy** per Mac and per canonical vault file in a new, versioned native-helper data-protection keychain item, service `com.wydrox.apassy.owner-policy`, account derived from canonical file identity and vault UUID. Match the existing per-file unlock-account model while also binding vault identity. Replacing/restoring/moving a file conservatively falls back to Every time until the owner configures it again. No automatic propagation to another path, vault, Mac, or iPhone.

Use a non-synchronizing `ThisDeviceOnly` item restricted to the signed Apassy helper's access group. A policy read must not itself require biometry: it is configuration, not a stored passphrase. Do not put its effective value in editable `ui.json`, UserDefaults, extension storage, relay data or a synced vault table. A 0700 directory alone is not protection against the same-user process that can edit preferences. The signed helper already checks the parent app before **every** command (`native/ApassyHelper/main.swift:63`, `Caller.swift:67`); preserve this for the new API. An agent cannot use the helper as a policy-writing oracle.

A setter requires a fresh new action, `ChangeOwnerCheckFrequency { vault_identity, old_policy, new_policy }`, verified by the existing local gate, never by grace/remote/CLI. The app invokes a narrowly typed helper write only after proof validation and rechecks the current identity/policy on completion. Do not add a second helper biometric check after the Rust check. No generic keychain read/write endpoint and no policy setter through the owner socket, browser socket, MCP, relay, or iPhone.

Missing, corrupt, unknown-version, unreadable or wrong-identity policy => Every time. A no-keychain build remains Every time and explains that timed verification is unavailable. Write/readback failure forces Every time for the current process, clears the active window, and displays a failure; do not show success optimistically. The previous stored choice may still be present after an unsuccessful change and can be read on a later launch, so explicitly say the choice was not saved and allow retry. A restart never restores an active window. Read back the saved item. Do not offer a plaintext preference fallback. Release builds retain no caller-check override.

The **active owner session** is separate, memory only, with no passphrase, secret value, LAContext or usable bearer token. It is never saved or synchronized. Compromise of the signed app or owner account remains outside the protection claim; keychain protects stored policy from ordinary unauthorized edits, not a fully compromised trusted process.

### 2.3 One central enforcement point

Add `OwnerSessionPolicy/OwnerSessionState` (suggested new `src/broker/approvals/owner_session.rs`) owned once by the app and shared by `Arc` with every `OwnerGate` clone. **Do not create independent sessions inside each `owner_gate()` call**: it currently constructs a fresh gate at `src/desktop/owner_check.rs:1497`. Broker and relay gates may share the invalidation state, but cannot spend it.

Central authorization remains `OwnerGate`. Add an internal typed authorization context that can be created only by the local controller after an exact action confirmation and live verified browser ticket. It is not a new serializable `OwnerCheck::Grace` value. Do not infer eligibility just from `OwnerAction::FillLogin`, a boolean, or a socket command. Default all unknown/new actions to FreshRequired. Retain normal `authorize/authorize_cancellable` semantics for all existing callers.

Proposed state: `{ canonical_vault_identity, vault_epoch, policy_version, session_generation, verified_at, absolute_deadline, local_login_session_identity, lifecycle_generation }`. `verified_at` is measured with an injected monotonic/continuous clock; wall-clock adjustment cannot lengthen it. If a Rust clock stops during sleep, the observer invalidates before resume; observer health/session-state checks must fail closed. The window is **absolute**, not sliding: reuse, browser traffic and UI activity cannot extend its deadline. A fresh eligible browser check after expiry can start another window. Unlock, reveal, settings change, agent approval or remote signature cannot start one.

Algorithm:

1. Validate vault unlocked, request identity, origin/account/revision, source guard, ticket liveness and local login session before consent/authentication. Keep one pending owner dialog; never replace one the owner is reading.
2. Snapshot policy, vault epoch and invalidation generation. If Every time, untrusted/missing provenance, observer unavailable, or action outside allowlist: run existing fresh T/P flow. If eligible but no live window: show the exact action's fresh T/P prompt. Only successful **local** verification can start a window for this scope.
3. While a valid window exists, show the exact local confirmation described below. A click for that dialog identity/action creates a private one-use consent capability. No app button is clicked automatically by a native request, extension message, notification, or timer. No global “Approve all” button.
4. Under the gate's shared state, recheck every binding and mint a **new one-action proof**, with internal provenance `RecentLocalVerification`, bound to the session generation/deadline and consent identity. Never clone or renew an old proof. Fresh-path proof still has current semantics.
5. At consumption, `OwnerProof::check` must verify the grace-derived proof's generation and absolute deadline as well as action and vault epoch. Its validity is at most `min(PROOF_LIFETIME, remaining_window)`; expiration/lock between issuance and secret read prevents execution. Existing 60-second proof lifetime must not accidentally extend a one-second remainder.
6. Recheck source ticket/deadline immediately before the vault operation and before delivering a response. Recheck current item/site/revision just as today. Explicitly extend this cancellation behavior to timed save/create as well: current `needs_live_ticket` excludes them (`owner_check.rs:560`), and BrowserWire's watch list is narrower than all these operations (`browser.rs:107`). A disconnected create must not silently leave an unintended login; once saved, a failed delivery is reported accurately and never automatically regenerated.
7. Only successful applied routine browser authorization maintains its already-fixed window; failing/cancelled attempts invalidate it. Count real identity checks separately from local action confirmations and reuse hits. Existing ADR 0025 question/interaction counts must not be relabelled as biometric counts. Store no domains/accounts/values in new aggregate prompt metrics.

Concurrency: never hold a vault or session mutex across LocalAuthentication or native/network waits. Use one ordering for short nested critical sections: vault mutex, then owner-session mutex. Snapshot/release/authenticate/recheck. An invalidation increments the generation and cancels in-flight dialogs/consents, so a late successful helper result cannot resurrect a window. Proof consumption after invalidation fails even if it was queued before a repaint.

### 2.4 Invalidation and lifecycle

Every mode ends earlier on the following. This is core enforcement, not cosmetic UI state.

| Event | Required behavior |
| --- | --- |
| Manual vault lock, CLI lock, backup, restore, vault switch, rekey, close | Clear state before the lock/switch proceeds; preserve vault epoch checks and cancel pending tickets/proofs. Hook below UI actions too, since multiple entry points lock the vault. |
| App quit, crash, restart | State is memory only. No resume from saved UI state; next action freshly verifies. |
| Mac screen lock | Invalidate immediately, cancel in-flight reuse, require fresh verification after unlock. Recheck current session lock state before spending a window. |
| Sleep / display sleep | Conservatively invalidate on either; wake never restores it. |
| Fast user switch / login session resigns active | Invalidate before any more use; returning to same user still needs a new eligible check. |
| Policy change, even to a shorter duration or back to Every time | Invalidate pending and active sessions first. Existing generation cannot survive a new policy version. Fresh setter check does not seed a new browser window. |
| Authentication failure, cancel, timeout, helper loss, source/consent validation failure | Clear window and drop pending consent. A failed check on another path cannot leave a browser grace session usable. Passphrase fallback may establish a new eligible session only after success and a rechecked live request. |
| Native lifecycle watcher exits, disconnects, sequence gap, cannot determine lock/session state | Fail closed to fresh verification. No grace until trusted observation and active/unlocked local session are established again. |

Implement a signed, caller-checked **long-lived lifecycle event stream**, not an egui focus heuristic. The existing native helper is invoked per request (`src/native/mod.rs:1134`, `:1388`), so it is not already a durable observer. Proposed new `native/ApassyHelper/OwnerSessionLifecycle.swift` with a dedicated streaming mode and `src/native/owner_lifecycle.rs` client: observe workspace sleep/display-sleep and session resignation; observe screen lock with an OS-state check at authorization time. Include a ready snapshot and monotonic event sequence. Screen-lock notifications alone, especially undocumented distributed notification names, are not a sufficient security claim; unsigned other processes must not spoof an **unlock** that restores authority. Events can always revoke, never grant. Verify the chosen OS session APIs on the project's actual supported macOS targets before implementation acceptance. Native helper exit revokes. Do not equate Apassy losing focus (normal while using browser) with the Mac locking.

### 2.5 Extension, host, native provider and iPhone

- **Extension:** no timer, password cache, owner-session token or policy writer. Preserve per-action popup/inline choices and target attestation. It sends a request and awaits app consent/authentication as today. Page-generated passkey bridge events remain untrusted and always fresh. A page has no way to claim recent verification. The app may return non-authoritative display metadata such as “Confirm in Apassy”; no session deadline is an authorization capability.
- **Native host:** remains a bounded forwarder, no cache. Require the existing signed parent/peer guard for *all operations eligible for reuse*, on both host and app sides. `GUARDED_COMMANDS` is currently only passkeys/codes (`src/browser/wire.rs:136`). Never use the extension-origin CLI argument as authentication (`src/browser/caller.rs:3`). Guard failure may keep the old fresh-auth path where supported, but can never grant reuse. Keep hangup cancellation for all timed operations. Browser code signing and debug-argument checks reduce injection routes; they do not prove physical human presence.
- **macOS AutoFill:** retain fresh checks, same exact native request IDs and provider flags. No changes to native provider verification contract in this feature.
- **iPhone:** no new frequency setting, no synchronization of Mac policy/session, no reuse of Mac authentication. Retain F/P for local secret actions and SE per signed approval; keep approval keys at zero reuse. Retain existing batch unlock LAContext only for its unlock reads. Do not add a Face ID preflight before SE signing: the signing operation is already the check. Relay signature freshness, first-valid-answer, expiry, replay and team policy remain unchanged.
- **Agents:** never get passwords back, a clipboard route, owner-session state or a way to mark a request human. Existing approved process real-secret delivery and placeholder semantics stay as documented. The bouncer and durable explicit permission mechanisms remain responsible for reducing agent questions, not this window.

### 2.6 UI flow and exact copy

This is a settings component spec, using the existing Settings > Security row groups (`src/desktop/ui/settings.rs:546`). No new tab, category dashboard or onboarding sequence. Primary user goal: complete a cluster of browser tasks without repeated fingerprint checks while retaining control over each disclosure. The owner arrives frustrated; success is obvious at the next routine browser action (**Feedback Loop**). There is no conversion goal.

**Settings screen:** after Unlock/passphrase rows, a group **Browser approvals**. Label **How often to ask**; values **Every time**, **1 minute**, **5 minutes**, **15 minutes**. Note: **“Use a recent identity check for browser passwords and codes on this Mac. You still confirm each action in Apassy. Passkeys and agent approvals always need a fresh check.”** Add **“For this vault on this Mac.”** Scope sits next to the control, not in a tooltip (**Recognition Over Recall**).

Changing a selection creates a draft; one **Save** button applies it after fresh verification; **Cancel** restores previous selection. Setting-change prompt: **“Change how often Apassy checks your identity for browser actions to 5 minutes?”** Supporting text: **“Browser actions will still ask you to confirm. Passkeys and agent approvals are unchanged.”** Authentication reason: **“change how often browser actions require identity verification”**. No extra confirmation sheet before that fresh check. Success: **“Saved for this vault on this Mac. The next browser action checks your identity.”** No celebration/toast fanfare for a routine security preference.

**First eligible browser action / expired window:** existing site/account/action prompt plus **“After this check, browser passwords and codes can use it for 5 minutes. You will still confirm each action.”** The initial setting change itself is not the action that starts the clock. Every time mode keeps existing behavior/copy without a misleading reuse message.

**Active-window action sheet:** title **“Fill GitHub?”**; fields **Website: https://github.com**, **Account: rafal**; note **“Identity checked 2 minutes ago. No Touch ID needed for this action.”** Primary **Fill**, secondary **Cancel**. Save/Create/Update/Fill code use the exact corresponding verb and account/site, including mutation implications. Footer **“Identity check expires in 3 minutes. Locking or sleeping the Mac ends it sooner.”** Do not silently execute when this sheet opens, do not use preselected confirmation, and do not say “approved” until the action completes. A separate **Require a new check** secondary link clears the window and enters fresh authentication for this action. A revoked/expired sheet switches to **“Confirm your identity again to continue.”** before completion, with no stale active status.

**Other states:** locked = existing unlock route, policy unavailable = **“Timed identity checks are unavailable in this build. Apassy asks every time.”**, save failure = **“The choice could not be saved. Apassy will ask every time until you quit. Try saving again.”** Wrong passphrase keeps the field's existing recoverable error; timeout/cancel ends that attempt. Cancel from an active-window action invalidates the window, so the next action freshly checks. Missing scope/no vault = disabled control with **“Unlock a vault to change this.”** Updating a policy must never optimistically show it as effective.

Keep keyboard navigation, VoiceOver value/selection, origin/account text and full site disclosure accessible. Use existing egui sizes/focus conventions; confirmation target at least 44 pt, Cancel safely reachable, no countdown announcements every second. Status must not depend on color. UI state is presentation only; expiry/revocation is enforced in the gate even while the window is hidden or covered.

**Flow:** Settings → choose duration → Save + one fresh check → Saved. Later: browser action → fresh check (first time) → action complete → next browser action → one local confirmation without biometric → action complete. Any invalidation → next eligible action freshly verifies. End state is the completed fill/save with a true result and an exit back to the browser. The owner should be able to say: “I confirm each browser action, but I only verify my identity every five minutes.”

**Experience/ethics check:** current entry frustration −2; finding the scoped control 0; one setup check −1 with explicit reason; first reused action +1; task complete +1. The intended improvement is fewer repeated identity checks, not fewer informed choices. Default Bias passes transparency (plain scope/exemptions), symmetry (Cancel and Every time remain available), reversibility (freshly change back; lock immediately revokes), and alignment (the stated owner goal). Do not introduce silent broad opt-in, false urgency or “recommended” styling on an unsafe indefinite option. Informal usability sessions should include an owner who cancels or reverts, not only people who complete setup.

### 2.7 Threat analysis

| Threat | What changes / risk | Mitigation and honest limit |
| --- | --- | --- |
| Agent calls browser.sock directly during a window | Legacy fill/save/create/update are not all signed-peer guarded today. Naive cached `OwnerAction` authorization would expose secrets or mutate vault without a new human check. | Signed guard required for reuse, internal provenance, exact local app click, live ticket, action allowlist; direct/legacy/source clients remain FreshRequired. An agent cannot spend the window via MCP, CLI, relay or arbitrary `OwnerGate::authorize`. |
| Malicious page synthesizes bridge/inline requests | JS events are not physical-presence proof. Quiet cached passkey signing would turn page code into account authentication. | Passkeys always fresh; ordinary password/code actions retain exact app confirmation. Preserve document/frame/form/origin validation in extension and app. No auto-submit or automatic consent. |
| Malware / automation controls trusted browser or accessibility UI | A signed browser is not a trusted human. Another extension or accessibility automation may act during a window; biometric removal weakens identity assurance. | Keep local confirmation with recognizable site/account, short absolute cap, guard's debug/injection checks, protected bundle/profile, clear active state, immediate lock/recheck. Full owner-account/accessibility compromise is not solved. Do not claim “human-only” as a proven property or fill in a browser controlled by an agent. |
| Stolen unlocked Mac | Holder may confirm routine actions without biometrics until timeout. | Default Every time; at most 15 minutes, revoke on screen lock/sleep/user switch, visible action scope; reveal/copy/passkeys/export/production remain fresh. Strongly distinguish this residual risk from encrypted-vault-at-rest security. |
| Policy file edit by local process/agent | Editable UI preference could select long duration and persist a silent relaxation. | Store effective policy in caller-restricted device keychain; fresh setter; no external write API; fail closed; no plaintext fallback. Root/trusted-app compromise is outside the claim. |
| Delay, replay, concurrent cancellation, lock then late auth success | Existing exact proof checks alone do not know a new owner-window generation/deadline. | One-use consent identity and new per-action proof; gate and consumer check generation/deadline; invalidation cancels helpers/tickets; no resurrection from late tasks. |
| Clock rollback / missing sleep event / observer failure | Fixed window might last longer than described. | Monotonic timing plus trusted current login-session/lock check; sleep/watcher loss invalidates, not pauses. Never restore from disk or an “unlocked” event. |
| Relay/iPhone answer rides the Mac's window | Remote approval would lose per-answer hardware proof and could cross teams/vaults. | No reuse or seeding for Companion/Remote/RemoteAction; preserve signatures/nonces/age/digests, device revocation, team scope and first-valid-answer rules. |

This is an explicit weakening of identity frequency for eligible human browser operations, accepted only when the owner opts in. “Agents never receive passwords”, no agent pasteboard path, app-side password generation, and exact-action/epoch proof checks remain requirements. Browser-fill passwords still become readable by page scripts/other software controlling that browser after a legitimate fill; the setting does not solve that existing limit.

ADR 0021 §6's claim that browser-driving automation cannot fill without fresh biometrics must explicitly narrow to Every time; timed mode relies on local consent and has the limitations above. Keep ADR 0024 where still applicable, with ADR 0025's already-recorded supersession of first-use behavior.
