# Implementation plan — iPhone access requests (ADR 0033)

Date: 2026-11-01. Status: implementation in review. A-C are separate protocol/lifecycle/transport commits; D adds typed Core calls and durable submission guards; E adds fresh cancellable signing and native Requests; F adds synthetic integration/UI evidence. Physical-device acceptance below remains pending.
Decision: [ADR 0033](../adr/0033-iphone-access-requests.md).
Wire: [relay-access-request-v1](../contracts/relay-access-request-v1.md).

## Outcome and constraints

An owner can read an authenticated access-request card in iPhone Requests, Deny without Face ID, or Allow once with a fresh Face ID signature. The asking Mac commits the first valid answer and alone issues/consumes one scoped access permit. The eventual command still goes through the bouncer. The Mac UI/CLI remain available, durable grants stay local to the Mac, and relay unavailability never prevents local decisions.

No product code, schema change, release version, production relay mutation or deployment belongs to this design PR. Future work uses synthetic vaults/credentials and fake relays for automated tests; physical signing checks are a separate acceptance boundary. Do not run test containers on this Mac or on the production VPS.

2. Live Mac and iPhone trusted rows in the vault; exact per-team relay device mapping; an iPhone `answer_key` confirmed by the Mac after the existing owner check. A relay-reported device or role is insufficient.
3. Per-team answer signer selected by the key actually registered in the row, including reconnect/revocation/enrollment-change behavior. Access requests must not register their own keys.
4. Question-key availability/rotation, push setup, membership cancellation and local fallback follow Connect's completed lifecycle. A half-connected phone cannot approve.
5. Connect handoffs retain separate dispatch and never appear as run/access requests. The carrier quota tests include handoff traffic; the new access publisher cannot assume the whole questions budget is free.

Define strict card/answer/settle types and exact digest/signature builders, bounded parsing, the outer-carrier dispatch enum and status/error vocabulary. Include actual `vault_id` and Mac-assigned host-label provenance; freeze lossless canonical path handling and exact normalized host/port equality independently of the proxy's subdomain policy. Freeze `policy_digest` with an explicit versioned serializer of the existing authorization baseline's fields; document every included field, including agent/token generation and trust-key/mapping fences, without standardizing Debug output. Freeze the optional MCP `scope`, run `access_request_id`, non-creating agent-authenticated status/cancel calls and `AllowAccessOnce` action scope with B. V1 use retries after admission are refused; do not invent execution idempotency from command equality. Share pure Rust helpers with ApassyCore where possible, following current crate feature boundaries; no dependency on the FSL relay crate.

**Acceptance (Rust):** exact byte vectors and independently verified signatures for both choices; negative mutations to every signed field including vault id, names/reason, host provenance and outer identity; duplicate keys/invalid UTF-8/unknown fields, scope overflow, wrong signature key, cross-run/feed protocol replay and wrong AAD. Test `now-55/now-56/now+5/now+6`, creation/exact-expiry boundaries, long signing prompts and clock jumps. Prove a new inner card cannot be parsed as `PendingRun`, while existing questions digest/answer vectors remain unchanged. Signatures/digests must operate on exact body bytes, not reserialized JSON. Deliver the vectors before B/C/D consume the protocol.

### B — Local request lifecycle, owner gate and one-use broker admission

**Own:** `src/agent/{mcp,wire}.rs`; `src/broker/decide.rs`, `src/broker/approvals/owner_auth.rs`, `src/broker/run.rs`, `src/broker/mod.rs`, `src/broker/proxy/{mod,swap}.rs` as needed; proposed `src/broker/access_once.rs`; `src/vault/access.rs`, `src/vault/agents.rs` and schema registration/local-table declarations; `src/desktop/owner_store.rs`. Connect's in-progress staging uses schema 21: allocate the next free schema after its merge. Tests extend `tests/access_model.rs`, `tests/agent_run.rs`, `tests/owner_auth.rs`, proxy tests and inline MCP parser tests; a new `tests/access_requests.rs` must be registered as a module in `tests/it.rs`, the single integration-test target.

Add a versioned local scope/lifecycle table and receipt/tombstone storage; preserve legacy notes and do not broadcast them at migration. New scoped requests have fixed expiry, exact-scope coalescing and durable rolling creation counters **per Mac/local vault**, not a distributed quota. Reserve creation/cooldown budgets atomically before export; denial/cancel/failure/restart/clock rollback cannot refund them. No permit authority is persisted or synced. Make one arbiter own answer/cancel/expiry/invalidation and burn; integrate durable `set_exec_grants` request-answer transitions transactionally so a losing dialog cannot create a grant. Keep standalone fresh local grant actions possible after a closed request without treating them as another answer. Agent status/cancel are authenticated and non-creating; disconnect alone leaves the asynchronous request alive.

Add new non-Clone exact-action proofs for local fresh `AllowAccessOnce` and remote `RemoteAccessAnswer`; do not add access allowance to ADR 0030's window allowlist or use general remote `ChangeGrant`. Record the remote check method and answering device/key/mapping. Recheck fresh trusted device and scope at commit/consumption. Run references are agent-scoped, one-item admissions; mismatches do not fall back. Assign a private operation identity, consume before downstream routing, and never restore after failure. Repeated use calls after admission fail, including existing equal-text question retries; the caller uses status. Carry an operation-bound admission fence through all model/owner waits, credential preparation/delivery and spawn; cancellation/expiry/key or token rotation/revocation still refuses after consumption, and a later run question cannot extend it. At every placeholder substitution enforce that fence and exact card hosts/ports intersected with binding policy; existing suffix-based `HostRule::covers` alone is insufficient. Keep real-value confinement limits explicit. The bouncer's current routing/hard checks stay authoritative. Never/Only restrictions are not bypassed.

**Acceptance (Rust):** one winner in local-allow/local-deny/two-iPhones/durable-grant/expiry/cancel races; loser has no DB or permit side effects; exactly one admission under concurrent consumers; identical or distinct use retries cannot rejoin after consumption, even after lost responses or spawn/model failure; no permit revival after lock/restart/rekey/restore or a failed commit. Changed item revision/binding/agent/token generation/policy/project/action/host/answering key/team mapping/clock/deadline fails closed. Expiry/revocation/cancel after admission or during a run question prevents secret release/spawn and never refunds authority. Dynamic subdomain, alternate port and redirect credential substitution fail outside the exact approved set, including when the broader binding permits them; normal unreferenced proxy behavior stays compatible. No writes to durable grant/owner-answer/pattern/declaration/exception tables from phone allowance. A valid access permit plus a bouncer veto still asks/refuses; `can_use` remains usable without a new prerequisite. Hidden items stay indistinguishable from missing ones. Remote allow/deny neither seed nor consume an existing owner window; local access-consent stays fresh even in a window. Migration retains old notes without creating authority. Test quota edges with concurrent creates, cancellation loops, failed dispatch, rollback and independent Macs; status/cancel never create requests or leak another agent's id.

Publish Mac-signed encrypted cards from eligible open requests with remaining lifetime greater than 10 seconds, using current membership/key. Add an **Access requests** distinction to Mac Decisions; do not reuse requests for pasting missing credentials. Local fresh Allow once, Deny and durable Mac grant actions all use B's arbiter. Keep CLI compatibility with explicit exact-request proof/receipt semantics. Generic relay pushes have no request identity: clicks open/refetch the Requests inbox and require row selection. In-app row navigation binds exact `(vault_id,asker,request,qid)` identity, never the next/newest row.

Process only new inner access answers from exact live trusted iPhone mappings. Verify typed owner proofs and settle with the actual winner. Never trust relay sequence/timestamp/role as the winner. Keep local outcome on relay failure; retry one immutable signed settle envelope. Show confirmed device attribution, exhausted/expired permit status and local-only reason when export fails. Keep companion denial routed through the arbiter without extending its wire protocol.

**Acceptance (Rust + headless desktop):** fake relay normal/offline/delay/drop/reorder/replay, two-iPhones, answer-first/local-first/cancel-first and grant-race tests; stale/revoked device, changed epoch, removed mapping/key, malformed/oversized card, `404/403/413/409` and full relay budgets. Lost POST response cannot make a second request or permit; lost or expired settle cannot reopen. Delayed receipts after use/cancel/crash confirm only historical consent, never live availability. A near-expiry committed answer survives a refused settle without asserting remote confirmation. Generic notification taps cannot select any card; exact row navigation and local card remain usable. Existing run relay tests, companion denial and owner CLI grant tests remain green. A signed card proves Mac source; a forged card signed by a different vault device or relay-supplied key is rejected.

### D — ApassyCore and typed Swift transport

**Own:** `ios/ApassyCore/src/core/questions.rs`, its `questions/envelope.rs`, `core/request_history.rs`, proposed `core/access_requests.rs`, dispatch in `core/mod.rs` if needed; `ios/ApassyVaultKit/Sources/ApassyVaultKit/{Questions,VaultService,PreviewVaultService+Questions}.swift` and `Sources/ApassyVaultCore/CoreVaultService+Questions.swift` with their mocks/tests (reconcile moves after Connect); `docs/contracts/ios-core-v1.md` for the new callable interface, in the implementation PR only. Tests: `ios/ApassyCore/tests/{questions_flow,multi_device_questions,requests_compatibility}.rs` plus new access cases.

Add a typed access-card variant while keeping old run result shapes compatible; use new calls or a capability/version boundary instead of silently changing strict old DTOs. Calls prepare immutable scoped bytes and return signer choice; core signs denial with the relay identity and verifies an externally provided Allow once signature with this vault/team's registered answer key before posting. Separate actual vault ids/contexts and exact request identity throughout preparation, retry and receipt verification. Serialize answer posting; count all attempts across choices/uncertain responses against the three-POST budget, stop after success, and do not reset the budget on model refresh/background. Mac-signed card/settle verification happens in the core before Swift gets actionable data. No API returns secret values or a permit, or reports live permit availability from an immutable settle.

The inspected request journal takes run `Card/Choice/Settle` types, including the legacy unsigned run settle. Add a type-discriminated access history projection and guard interface rather than casting access results into those types. Preserve old history with a compatible migration/version boundary; no run receipt can confirm access consent. Reserve submission attempts durably before POST even when optional history is off; history clearing/restart cannot reset a live guard. Retain only bounded encrypted metadata, not signatures/permits, and fail closed if guard storage cannot be updated. History remains non-actionable and never supplies authority.

**Acceptance (ApassyCore):** drive real JSON API through fake relay using A's same vectors, complete request/deny/allow/settle flow, wrong vault id even with matching team/key/display name, wrong team/asker/qid, mixed run/access cards, missing registration, expired/unconfirmed receipts and unsupported older core. Simulate append-only answer POSTs, lost responses and three exhausted attempts; no concurrent/repeated-after-success POST or fourth automatic attempt is allowed, including after restart, history clearing, history opt-out or guard-write failure. Unsigned run settles and old history cannot confirm access or revive its controls. Background/suspend/select/remove must discard prepared signatures and authority; stale completions cannot post into a new context. A delayed/replayed accepted answer never reports an available permit. Existing multi-vault questions, request history and run-answer compatibility tests pass unchanged.

Use the ADR's exact labels, full critical facts, provenance and denial-only incomplete state. No durable button, menu item, swipe or notification answer is added for an access card. Keep run controls type-specific. Prepare the exact answer then call the per-team protected signer with a new zero-reuse context; require Face ID type and the private key's Secure Enclave current-set ACL, not a UI-only prompt or `.userPresence`. Wire lifecycle cancellation to `LAContext.invalidate()` during pending signing and on every completion path; ignore late results. No passcode or production software-key fallback. **Acceptance (Swift models):** Allow once calls only the correct answer signer and exactly once per new choice; unlocking/previous signing does not satisfy it; Deny never calls that signer. Assert pending-context invalidation, not only discarded results. A transport retry reuses the same signed choice within its bound and three-POST budget; a user-selected new choice calls for a new match, never an automatic prompt. Multiple vaults/teams pick their own registered key. Unsupported core or missing trust gives local-review copy with no Allow once.

**Acceptance (iOS UI tests):** synthetic access request alongside a run request and a missing-credential request; complete facts and all hosts; distinct row/detail routing; Allow once and Deny only on the access detail; no durable options; actual expiry disables controls; Face ID cancellation is recoverable; pending/confirmed/other-device/expired/unconfirmed outcomes. VoiceOver order, accessibility text sizes, long similar paths/agent names, IDNA hosts, malicious control/bidi text, Reduce Motion, dark/light appearance and 44-point targets. Simulator tests validate UI/state, not actual Secure Enclave freshness.

## Implementation evidence and limits

The implementation is based on merged Connect #41 (`8e61e04`), schema 22. No relay source or carrier fields change. The owner accepted inherited time-sensitive pushes and conservative per-Mac quotas (one active/unconsumed scope per agent, 30-second creation cooldown, five/hour/agent, twenty/hour/Mac-local-vault, ten open). Run publication has priority; Connect retains its reserved handoff dispatch. iPhone submissions reserve one of three attempts durably before POST, even with history off. A receipt is historical consent only.

`tests/fixtures/access-request-v1/` contains independent byte/signature vectors. Root protocol/lifecycle tests, `tests/access_requests.rs`, `tests/relay_questions.rs`, `ios/ApassyCore/tests/access_requests.rs`, `AccessRequestsModelTests` and Simulator Requests UI tests cover their respective boundaries. See the implementation PR and review evidence for actual commands/results; this list alone is not a passing-check claim. Native screenshots use a synthetic scratch vault/fake relay; iPhone UI screenshots use in-memory fixtures and a simulated signing wait, not an OS Face ID match. Evidence destination: `/Users/rafalw/Dev/apassy/docs/reviews/audit-2026-10-31/impl-0033/`.

Exact run destinations currently require explicit HTTP(S) authorities and reject ambiguous destination flags, proxy overrides, IP literals and unparsed forms. Such runs remain available through ordinary Mac review without an access-request reference. This is fail-closed scope recognition, not broader networking confinement for real-value delivery. Generic vault labels are accompanied by the authenticated vault UUID; display names never select authority.

The #41 follow-up offers Remove/Keep after pairing when another iPhone has the same display name or is in the questions team. Keep is inert; Remove uses the existing revoke path after a fresh owner proof bound to the exact trusted row and questions team. No auto-revocation or answer-key renewal is introduced.

Physical acceptance still requires the isolated signed Mac/iPhone procedure in F: fresh Secure Enclave Face ID every time, no passcode/Touch ID fallback, direct signing failure without a match, enrollment invalidation/reconnect, native prompt cancellation, APNs routing and offline/two-phone device races. No TestFlight upload, production relay use or owner-vault evidence is included.

Review hardening: access publication reserves at most one unsettled relay slot per asking Mac, including uncertain POSTs, leaving nine for eight concurrent broker operations and one Connect handoff. Other access cards stay available locally with the original deadline. Expiry or confirmed settlement frees the slot. Explicit MCP operation cancellation withdraws its scoped card; disconnection or a lost response alone does not. Pending Face ID is invalidated at the signing/request deadline and on task cancellation.
