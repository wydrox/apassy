# ADR 0027 — Authenticated owner Copy on the desktop

Date: 2026-10-17.
Status: ACCEPTED by the owner on 2026-10-17: “Add authenticated Copy (Recommended)”, after reviewing the fresh-check requirement, conditional 30-second clearing, and exposure to other local apps ([decision record](../reviews/desktop-copy-decision-2026-10-17.md)). Implementation is part of the current main-flow work; acceptance here is not a release or physical-device verification claim.

## Context

Desktop reveal and browser fill already require a fresh owner check. The desktop previously copied only one-time codes; a person using a token or another secret manually had no direct Copy action. The owner accepted deliberate clipboard disclosure as another human action. This supersedes the desktop restriction in ADR 0021 §1. It does not extend an agent, broker, proxy, sandbox, or owner-socket API.

## Decision

- A supported secret field offers **Copy** beside its masked value. Copy works without revealing first. Passkey private material, including reserved `passkey_` fields, and TOTP setup keys are excluded; the existing **Copy Code** action copies only the current one-time code.
- Every Copy starts a new Touch ID or vault-passphrase check. `OwnerAction::CopyField { item_id, field, revision }` binds the proof to the exact item, field, and revision in the current vault session. It cannot reuse a reveal, fill, code, other-field, or other-revision approval. Cancellation, lock, vault switch, a deleted item, or a changed revision prevents the read.
- `OwnerSession::copy_field` consumes the proof, revalidates the field and revision under the vault lock, and returns an erasing buffer to the trusted desktop clipboard adapter. It does not populate the revealed-value cache. No secret enters the request identity, proof, result message, log, or persistent clipboard record.
- The native helper receives `clipboard_write` with `secret_b64` and a caller-generated random 128-bit `owner` marker (32 lowercase hexadecimal characters) over stdin and writes UTF-8 text to the macOS pasteboard. Its caller check admits only the signed containing Apassy app. It returns only that marker and pasteboard `change_count`, never the text. A lost or malformed write acknowledgement triggers best-effort cleanup using the already-known marker. See the [helper contract](../operations/native-app.md#helper-protocol).
- The app shows “Copied. Clears in 30 seconds if the clipboard still holds Apassy's copy.” It requests clearing after 30 seconds and on lock, vault switch, and quit. Normal clearing requires the same owner marker and `changeCount`; a later copy, including identical text, has a different write identity and must be preserved. A failed replacement retains the pending clear of the previous write. Lost-acknowledgement cleanup compares the known marker and stable current count without needing the missing response count. A failed expiry clear erases local text and keeps only the identity for a later retry while the app runs.
- Concealed, transient, autogenerated, and remote-clipboard exclusion markers request privacy behavior from cooperating software. They are advisory. They do not enforce secrecy or prove that remote sharing, clipboard history, or another process retained nothing.

## Exposure and limits

Copy is deliberate disclosure. Another local app can read or retain the text during its lifetime, and clearing cannot retract that copy. macOS `NSPasteboard` has no interprocess atomic compare-and-clear operation: the helper checks the count and owner marker immediately before clearing, but another process can write in the final interval. Conditional clearing reduces interference with later copies; it cannot guarantee its absence under concurrent writers. Process termination or a helper failure can also prevent clearing. Swift, AppKit, pasteboard, allocator, swap, and crash-dump copies are outside the erasing-buffer guarantee.

The broker, proxy, sandbox, automatic agent APIs, and owner socket continue to return no secret values. Browser fill remains separately authorized for its origin and target. Copy approval never grants an agent permission to retrieve a value.

## Validation boundary

Synthetic owner-session and in-memory clipboard checks must cover proof mismatches, cancellation, changed items, expiry, lock/switch, replacement writes, and later identical text. Execution results belong in the current validation ledger. They do not prove Touch ID, the signed helper, Universal Clipboard behavior, or clearing on the owner's physical Mac. No production secrets or live pasteboard are required for the synthetic checks.
