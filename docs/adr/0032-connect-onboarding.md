# ADR 0032 — Connect onboarding without an account

Date: 2026-11-01.
Status: ACCEPTED for implementation by the owner ("Build it now"). Local implementation and synthetic verification; real-device cellular approval and APNs delivery remain acceptance checks.

Free and Personal vaults can receive iPhone approvals and push without an operator code, an account, Stripe, or paid relay sync. The Mac's Settings > Devices offers **Get approvals on your iPhone**. Connect creates a questions-only membership with signed `POST /v1/connect`. Existing operator-code creation and paid relay-sync membership paths remain supported.

## Durable creation

Schema 21 adds the local-only `relay_connect_pending` row to the SQLCipher vault. The P-256 private key and original request labels commit before any network write. Locking, quitting, offline failures, and a lost response never rotate it. Sync exports and adopted copies strip it, like `relay_membership`. A successful response is saved before membership adoption, and later re-enabling reuses the saved identity.

The creation signature is DER ECDSA P-256/SHA-256 over `apassy-relay connect v1\0<origin>\0<public key b64u>`. The legacy body omits `recovery_nonce` entirely. A transport failure gets one bounded retry with the same key. On `409 connect_key_used`, the app probes `POST /v1/connect/challenge`. A supported challenge must match the origin and contain a valid fresh nonce; its proof appends `\0recovery\0<nonce>`, and the request includes `recovery_nonce`. This implements the relay's F06 recovery extension without a version gate. A relay without that route gives a clear recovery-unavailable error and retains the key; it never silently creates another team. Removed/suspended teams are not recreated by recovery.

Daily capacity, total capacity, network creation limits, offline status and recovery failures have distinct messages. A short edge limit uses the relay's Retry-After seconds rather than claiming the daily capacity is exhausted. The displayed 50/day, 100 total and up to 5/network/day values are documented defaults, not observed production settings. Connect membership has only `questions`; the relay's Connect preset has `sync_bytes=0`. No snapshot or sync receipt is sent by this flow.

## Confirmed iPhone join and key handoff

The iPhone first opens the same vault from iCloud Drive, as the Free plan already requires (ADR 0023). The Mac shows one device link/QR. ADR 0019's device key, one-use ten-minute link, safety words, and owner-confirmed join remain the authority boundary. The iPhone sends its public answer key using the existing device-name encoding; its private answer key stays on the iPhone behind Face ID.

For Connect pairing, the URL fragment adds `&handoff=2.<qid>.<32 random bytes b64u>.<Mac ephemeral public key b64u>`. This is a secret capability and is stripped before every relay call. After confirmation the Mac registers the iPhone and sends its question key plus the live public device rows through the existing opaque question transport. P-256 ECDH combines a fresh Mac private key (never in the QR) with the confirmed phone's relay key. HKDF-SHA256 with the QR secret as salt derives the ChaCha20-Poly1305 key. A QR observer, including a malicious relay with a screenshot, cannot decrypt another phone's handoff. AAD binds the domain, full original link/origin, team, qid, both public keys and the encoded phone name/answer key. Six locally derived safety words authenticate this transcript using the shared key; the relay's legacy two words are used only for wire compatibility. Mac confirmation still needs a fresh owner check. Connect never copies its QR capability to the system pasteboard. Expiry is locally capped at ten minutes, even when a relay advertises longer. The relay gets no QR secret, question key, vault contents or answer private key. The transfer preserves original sync versions and rejects another vault, another recipient, another answer key, removed keys and removed rows. The iPhone does not report success until it has the authenticated handoff. Older plain links keep the existing encrypted-vault-sync key delivery.

The handoff uses reserved `key_id=c011ec7000000001`; both current request readers skip these transport records. It expires with the pairing link. Retrying sends the exact sealed record, and no additional device is created. The Mac must remain open until transfer succeeds. A failure after confirmation can require removing that device and pairing with a new link; reinstalling always requires a new link, a fresh answer key even if Keychain survived uninstall, and confirmation, and the old device should be removed in Settings > Devices.

The success screen offers Request Notifications through the existing APNs routes, then Open Requests. Registration success is not proof that an alert arrived. Local Mac approvals remain available offline. Access-request answer semantics and Wi-Fi retirement remain separate (ADR 0033 / ADR 0028).
